2. **Merge** — once your verdict + required CI align. Chain wait+head-guard+merge in ONE background bash whose until-loop is the task's FOREGROUND (an inner `&` subshell dies with the parent): `until [ "$(gh pr checks N | grep -c pending)" = "0" ]; do sleep 20; done; HEAD=$(gh pr view N --json headRefOid --jq .headRefOid); [ "$HEAD" = "<full-sha>" ] && gh pr checks N | grep -q pass && gh pr merge N --merge` — guard the legs that actually ran. **EVERY GATE IN THIS CHAIN MUST BE A POSITIVE TEST, and it was audited on 2026-09-03 against empty input to prove it** (admin's governor read `limits:[]` as a low value and upgraded billing on no data; the merge analogue would report a PR GREEN when the truth is that NO checks were reported — the always-passing check, firing precisely when something upstream broke). Audit result, with the evidence:
    - `gh pr checks N` on a ref with no checks prints **`[]` on stdout, the message on stderr, and exits 1** (verified on PR #84). So `grep -c pending` = 0 and **the until-loop exits immediately on absence** — that leg is a NEGATIVE test and is safe only because the next leg is positive. `grep -q pass` finds nothing and **blocks the merge**. Do not ever replace that leg with "no failures found".
    - The run-level chain actually used here (`[ "$CONC" = success ]` + an EXACT expected job count + full-SHA head guard) blocks on `{"jobs":[]}` because 0 ≠ the expected count, and blocks on a queued run because `conclusion` is `null`. Verified against a real empty GitHub response (`gh run list --branch <nonexistent> --jq length` → `0`).
    - **Never write an all-must-be-success test** (`[.jobs[] | select(.conclusion!="success")] | length == 0`): it is vacuously true on an empty set. That single shape is the entire fault class.
    - **The expected job count is a mechanism-determined value** (the workflow defines it) — derive it from `.github/workflows/ci.yml` or state it as a dated observation; hard-coding it fails CLOSED when a job is added, which is the safe direction but must be a deliberate choice, not an accident.
    - **Verify an empty-input guard by making it FAIL FIRST.** A guard that has never been shown to reject an empty array is the same class as the instrument this audit came from.
    - Note for this fork specifically: because dispatch runs do not attach to the PR rollup (#3), `gh pr checks` legitimately reports NO checks for PRs whose dispatch runs were fully green — so the generic recipe above correctly refuses to merge here, and the chartered path is run-level enumeration plus `--admin`. **An empty rollup here means "not wired", never "clean".** **Delete the remote branch ONLY after reading MERGED state fresh** (deleting an open PR's head branch silently closes it) [SSR]. Post-merge: branch delete → docs flips (BOARD.md + any status file, docs-only push) → memory iteration entry. **Never merge on an aggregator check alone — enumerate ALL check runs on the head (`gh pr checks`) and NAME + ATTRIBUTE any red (inherited vs introduced) before the chain arms** [SSR #666/#872].
3. **Maintain the durable docs** — **NEVER RESTATE A VALUE SOME MECHANISM DETERMINES** (charter/board/brief sweep, 2026-09-03). If a tool, governor, env file, manifest or live API decides a value — CPU sets and nice levels, model names or tiers, load thresholds, lease caps, deployment names/IDs/URLs, env var VALUES (names are fine), version pins — write the AUTHORITY and how to read it live, never the digits. **The dangerous case is the value that is currently CORRECT:** a wrong one is eventually caught by whoever it fails, while a right one in a document with no mechanism to stay right is indistinguishable from an enforced one until it silently stops being true — and the copy is the version people actually read. So "I checked and it is accurate" is not a clean result; the question is whether anything makes it STAY accurate. Where a value must appear as evidence, date-stamp it and say it is a record, not a maintained copy — **a dated observation is evidence, a bare value is a claim; convert the claims, label and KEEP the observations rather than rewriting them into pointers and destroying the record.**

  **INSTRUMENT-CHANGE RULE (RM ruling 2026-09-03, first applied when the governor reached tier 2 and moved the lanes to `gpt-5.6-terra`; the harness-vs-judgement distinction and the ordering below were reconciled with the tsc RM, which correctly took the opposite line for its own series — a rule with visible provenance can be argued with, one that arrives as doctrine gets obeyed or ignored and neither is thinking).** A governor model switch never invalidates committed work and must never slow ordinary implementation. Where a lane is running a **measurement series**, three clauses in this order:

  1. **FREEZE THE METHODOLOGY IN THE BRANCH — always, and first.** Write the harness, thresholds, run conditions and arm definitions into the branch before any further arm is authored. This is the clause a lane can *execute*; the two below are conditions it can only *satisfy*. A rule whose compliance is a circumstance cannot be followed, only met by luck — so if a generation remembers one clause, it is this one, because it is the one that survives a governor switch nobody scheduled.
  2. **Additionally hold the model constant only where the reading is the model's OWN JUDGEMENT** — classifications, tolerance maps, allow/deny rulings, comparative censuses. There the **model IS the instrument, because the reading is its own output, and a mixed-model series is a mixed-instrument series however frozen the methodology is**; let it finish on the model it started with where that is possible (keep the lane busy to its natural freeze, or re-run the whole series). Lane B's #62 map — 40 catalog models classified in one series — is squarely this shape. This is the EXCEPTION, not the pattern. For **harness-produced** readings — frame times, latencies, benchmark numbers, coverage, threshold pass/fail — the model only authors the code that runs the arms, so clause 1 is sufficient and any model may author the rest; delaying such a series holds a variable outside the measurement path and costs real time.
  **DRIFT ADDENDUM (admin observation 2026-09-03, Codex weekly at 93%, resets 2026-09-08).** The spawn flag is NOT evidence of what ran. Across three fleets every working lane drifted monotonically toward a cheaper model at lower effort — lanes spawned `-m gpt-5.6-terra` and verified at spawn later read `luna medium` — with no governor touching reasoning effort and no drift back. Cause unproven and not ours to assert; the pattern is the fact. Consequences here:

  - **PREFER RE-DERIVABLE SERIES OVER BRACKETED ONES — this outranks the bracketing below.** Bracketing tells you a series is mixed; **re-derivability makes the mixing irrelevant**. Where a series' arms can be regenerated by a fence from pinned inputs — #86's census walks the pinned catalogs and re-derives every classification on each gate run — the result is checkable **without trusting whichever model wrote it**, which is the only property that survives an author you cannot identify. So when the RM specifies a judgement series in a brief, ask first whether a fence can re-derive its arms, and require that; bracketing is the fallback for series that genuinely rest on judgement alone.
  - **Never attribute a model from the spawn flag** in a commit message, ADR, PR body or series record. Record the READING and name the instrument that produced it: *"the status line reported luna medium"*, never *"written by terra"*. The status line is itself one signal and has disagreed with what an agent says about itself, so it is reported as a reading, not as ground truth.
  - **For judgement-produced series (clause 2), read the status line at the START and again at the END of the series, and report the series as MIXED-INSTRUMENT if they differ.** This is clause 3 meeting a variable none of us controls: the instrument can now change mid-series without announcement, so the only defence is bracketing the series with observations. Clause 1 (freeze the methodology) is unaffected and remains the actionable one.
  - **Do not read shallower lane output as a lane getting worse.** Varying quality under drift is a fleet condition, not a performance problem to correct in a brief or a verdict. Judge the work, not the lane.
  - Harness-produced readings are unaffected — the model authors the code, it does not produce the number.

  3. **Mixed-instrument arms that cannot be re-run are reported as MIXED, never averaged** — averaging across instruments produces a number with nothing wrong in it that describes nothing that happened. This clause outranks convenience: the un-re-runnable mixed series is exactly where every incentive points at averaging and calling it done. Name the model that produced each series in the series record — the PR body or the issue comment carrying the numbers — whichever clauses applied.

- **SANDBOX ROOTS ARE A PROPERTY OF THE PROCESS; THE ISSUE IS A PROPERTY OF THE WORK — GRANT AT PARENT LEVEL (2026-09-03, propagated from the suquo fleet).** A Codex lane's `--add-dir` roots are FIXED AT SPAWN and can never be widened afterwards. **Never grant a per-issue path** (`~/.dsh-lane-scratch/issue-<n>`): grant the PARENTS — `~/.dsh-lane-scratch` and `~/.dsh-resolver-worktrees` — so every per-issue subdirectory stays reachable for that process's whole life. Coupling a sandbox root to an issue number is the bug; granularity fixes it, vigilance does not. When a lane must reach something outside its roots, choose deliberately and say so: **respawn with new roots (costs a generation) or authorise a path it already holds AND STATE IT IN THE BRIEF (costs nothing)** — never let it discover your error through an error message and spend a turn diagnosing it.

- **ABSORBED FAILURES NEVER AGGREGATE (2026-09-03).** This class survives a day of hunting because every individual response to it is CORRECT: the worker hits the wall, works around it, discloses the workaround, and the incident closes cleanly — so the cost never lands anywhere anyone reviews. It is the inverse of the inert canary (which reports success while doing nothing): here failure is reported honestly every time and **the fault exists only in the sum, and nothing sums.** Robustness at a boundary destroys information upstream of it, so graceful degradation is not unambiguously good. **DETECTION: A REPEATED SELF-ATTRIBUTED GAP IS A STRUCTURAL SIGNAL, NOT A CHARACTER FLAW.** Writing "my gap / my oversight / my recipe was wrong" about the same SHAPE a second time is evidence of a mechanism — and nobody notices they are saying it a fifth time, because the sincerity of the self-blame is what stops the counting. On the second occurrence stop apologising, find the mechanism, then count the earlier ones: that count is the finding.

## LANE-FAILURE TRIAGE — CHECK THE BACKEND BEFORE THE LANE (2026-09-03)

**A Codex lane that fails inexplicably, or "completes" a turn with no output, is a BACKEND symptom until proven otherwise.** Fleet-wide outage precedent (2026-09-03): every Codex agent on the box returned `unexpected status 404 Not Found — https://chatgpt.com/backend-api/codex/responses`, Claude agents unaffected. **Read the lane's actual pane output FIRST; never let a lane spend a generation diagnosing an outage, and never respawn hoping a fresh session helps — the failure is upstream of the session.** A 404 on the responses path suggests a service/account change rather than an expired token (which returns 401), but the RM asserts the symptom, not the cause.

Three governor-side lessons from that outage, all of which apply to how the RM reads ANY instrument, CI included:

- **A MISSING VALUE IS NOT A LOW VALUE.** The usage source returned `"limits":[]`; a guard asking *does this field exist* (`jq -e` treats an empty array as truthy) passed, a `// -1` fallback produced a sentinel, and `-1 < 40` read as "the quota reset" — upgrading every lane to the priciest model and priority billing **on no data**. Ask whether a field CONTAINS what you are about to compare, never merely whether it exists, and render absence as `NO-DATA` so nobody can quote it as a figure.
- **A FRESH TIMESTAMP ON STALE DATA IS WORSE THAN SILENCE — but only for INGESTED timestamps (corrected 2026-09-03).** The distinction: a timestamp **we generate at sample time** (our own `date` when we take the reading, a filesystem mtime at write) is honest by construction and checking it is sound; a timestamp **we ingest** is part of the payload and can be exactly as wrong as the payload. Token counters were byte-identical while `updatedAt` advanced, so a staleness guard testing the timestamp could not see it: **the age travels with the sample and lies.** Corroborate a reading against something that moves independently of the reading's own metadata.
- **AN INSTRUMENT THAT HAS NEVER SHOWN A POSITIVE IS INCONCLUSIVE, NOT NEGATIVE.** A probe returning zero movement means "no signal", not "the answer is X" — the null is what surfaced the outage only because someone read the raw output instead of trusting it. See also the DRIFT ADDENDUM: two signals disagreeing is a known unexplained condition; record the reading and name the instrument, never the inference.
- **VERIFY BY READING THE STATE, NEVER BY THE COMMAND NOT COMPLAINING** — a `--force` that silently did nothing left a state file unchanged while the operator believed it restored. Same shape as `taskset` being re-asserted underneath a spawn pin and `herdr agent stop` leaving a Codex TUI alive: after any state-changing command, read the state back.

## CROSS-PLATFORM AWARENESS (owner standing rule, 2026-09-03)

The owner develops on Omarchy (this machine), Windows and macOS and moves between them. This product ships to all three, so treat it as cross-platform in PROCESS, not only in code. Binding on every review and every spawn brief:

- **Platform note in the PR.** A change touching build config, toolchain versions, native dependencies, filesystem paths, line endings, shell invocation, or platform-gated code must carry an explicit note on what it means for the other two platforms. The RM CHECKS that note as a review item — its absence on such a change is a blocker, not a rider.
- **Pins live in the repo.** Toolchain and runtime versions belong pinned in-tree so a fresh clone builds identically everywhere. Read the pins live, never from prose: `node -p "require('./package.json').engines.node"` and `.packageManager` for the declared range, `grep node-version .github/workflows/ci.yml` for what CI builds, `node -v` for what the lane is running. **Known gap (values as observed 2026-09-03, recorded as evidence for #87 rather than as a maintained copy):** `engines` admitted any Node ≥24 while CI built only on 22.23.2 and this machine ran 26.8.1 — a lane can produce artifacts and lockfile entries no CI runner or Windows checkout reproduces. Treat a widened `engines` range or a Node-version-sensitive change as a platform note item; consider a narrower pin when the owner next rules on it.
- **Lockfile updates are cross-platform events.** A lock written by a newer toolchain can be unbuildable by an older one (this bit the owner on Windows, 2026-09-03). Any `yarn.lock` change is reviewed as a portability change: say which Node and Yarn wrote it, and whether the entries it moved are platform-conditional (`optionalDependencies`, native builds — koffi, node-pty, electron, sharp).
- **Green CI is not proof of portability.** Say what the gate did and did not cover rather than treating a green rollup as portable. This repo is better placed than most — `check` on Linux, `desktop-windows` and `upstream-command-windows` on Windows, `desktop-macos` unsigned — but macOS runs only the smoke, no signed packaging, and no runner exercises the Node version the lanes develop on.

**LESSON — self-referential faults need an external observer or a deliberate audit (2026-09-03).** On one day, three repos on this machine carried three variants of the same fault, each invisible in a different way: suquo's toolchain pin was **absent**, this fork's was **present and loose** (#87), tsc's was **present and machine-local**. None of our gates could have found any of them, because **every gate runs on the machine whose configuration is the thing in question** — a gate cannot audit the assumption it is itself standing on. All three surfaced only because the owner hit an unrelated symptom on a different operating system and thought to mention it rather than quietly fixing it. That is luck, not process. The standing consequence: for any property that the local environment silently supplies — runtime versions, native toolchains, path semantics, line endings, locale, shell — the RM does not wait for a gate to complain. Either an external observer reports it (the owner's other machines, a CI runner configured differently on purpose) or the RM audits it deliberately, by reading the declared surfaces against each other the way #87 was found. Prefer the audit; it is cheap and it does not depend on someone else's bad afternoon.

## CROSS-FLEET QUIET WINDOWS (admin coordination, 2026-09-02)

Timing-sensitive measurement runs in ANY repo on this machine can request a short cross-fleet quiet window (`~/Documents/00-system-administration/tools/fleet-quiet.sh`, auto-expiring; the tool owns the maximum duration — read `fleet-quiet.sh --help`, do not restate a cap here). Both halves are binding here:

- **Honouring one.** On receiving `QUIET WINDOW (cross-fleet, until HH:MM)`, HOLD the start of any NEW heavy gate — `corepack yarn check`, full test suites, packaging/`dist:*`, browser suites, and any Codex lane spawn whose first act is an install or gate — until the release message or that time. In-flight work continues untouched and nothing is killed; light work (reviews, verdicts, BOARD/doc edits, `gh` reads, CI polling) is unaffected. Tell an affected lane to pause before its gate rather than killing it.
- **Requesting one.** For the RM's own timing-sensitive measurement (perf/latency incident work, an append-cost or trim measurement, a frame-timing observation), `fleet-quiet.sh request dsh-rm <minutes> "<reason>"`, then `fleet-quiet.sh release dsh-rm` the moment the measurement ends — never hold the lease for the analysis that follows. `fleet-quiet.sh status` shows the current lease and machine load; `is-quiet` is the scriptable check.

Rationale: a suquo frame-timing lane was competing with a core-pinned rustc compile on 2026-09-02 and neither RM could see the other. Numbers measured under contention are not evidence.

**CPU ALLOCATION — the load governor is the SINGLE authority (admin ruling 2026-09-03).** `tools/load-governor.sh` derives each process's CPU set from its repo/worktree path and re-asserts it every ~2 minutes. **Never pin a lane at spawn** — a spawn-time `taskset` survives at most two minutes, so a charter that named per-lane core sets described something the machine did not do, and which pin was live depended on where the timer happened to be. This charter has never carried such a table and must not acquire one; if a brief or a doc here ever names cores, delete the pin and leave the governor alone. Lanes keep `nice 10`. (`CARGO_BUILD_JOBS` is a Rust knob and does not apply to this Node/Yarn repo.)

  Two consequences that are ours to act on:
  - **Within-repo contention is the RM's to stagger.** Each repo is now contained to one band, so cross-repo contention cannot occur — but this fork's PRIMARY checkout (where the RM's `corepack yarn check` runs) and its lane worktrees share that band. **Do not run an RM gate and a lane gate at the same time**; serialize them, which the dual-spawn disjointness discipline already implies for the lanes themselves.
  - **Measurement work: the fleet-quiet lease is MANDATORY for definitive arms, and the receipt records the OBSERVED affinity read at run time** (`taskset -cp $$` from inside the run), never the affinity anyone assumed. A core budget that shifts under a running arm is an instrument change we would refuse from a lane — see the INSTRUMENT-CHANGE RULE — and the lease protects a measurement far better than a pin ever did.
