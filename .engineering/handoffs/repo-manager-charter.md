  **INSTRUMENT-CHANGE RULE (RM ruling 2026-09-03, first applied when the governor reached tier 2 and moved the lanes to `gpt-5.6-terra`; the harness-vs-judgement distinction and the ordering below were reconciled with the tsc RM, which correctly took the opposite line for its own series — a rule with visible provenance can be argued with, one that arrives as doctrine gets obeyed or ignored and neither is thinking).** A governor model switch never invalidates committed work and must never slow ordinary implementation. Where a lane is running a **measurement series**, three clauses in this order:

  1. **FREEZE THE METHODOLOGY IN THE BRANCH — always, and first.** Write the harness, thresholds, run conditions and arm definitions into the branch before any further arm is authored. This is the clause a lane can *execute*; the two below are conditions it can only *satisfy*. A rule whose compliance is a circumstance cannot be followed, only met by luck — so if a generation remembers one clause, it is this one, because it is the one that survives a governor switch nobody scheduled.
  2. **Additionally hold the model constant only where the reading is the model's OWN JUDGEMENT** — classifications, tolerance maps, allow/deny rulings, comparative censuses. There the **model IS the instrument, because the reading is its own output, and a mixed-model series is a mixed-instrument series however frozen the methodology is**; let it finish on the model it started with where that is possible (keep the lane busy to its natural freeze, or re-run the whole series). Lane B's #62 map — 40 catalog models classified in one series — is squarely this shape. This is the EXCEPTION, not the pattern. For **harness-produced** readings — frame times, latencies, benchmark numbers, coverage, threshold pass/fail — the model only authors the code that runs the arms, so clause 1 is sufficient and any model may author the rest; delaying such a series holds a variable outside the measurement path and costs real time.
  **DRIFT ADDENDUM (admin observation 2026-09-03, Codex weekly at 93%, resets 2026-09-08).** The spawn flag is NOT evidence of what ran. Across three fleets every working lane drifted monotonically toward a cheaper model at lower effort — lanes spawned `-m gpt-5.6-terra` and verified at spawn later read `luna medium` — with no governor touching reasoning effort and no drift back. Cause unproven and not ours to assert; the pattern is the fact. Consequences here:

  - **Never attribute a model from the spawn flag** in a commit message, ADR, PR body or series record. Record the READING and name the instrument that produced it: *"the status line reported luna medium"*, never *"written by terra"*. The status line is itself one signal and has disagreed with what an agent says about itself, so it is reported as a reading, not as ground truth.
  - **For judgement-produced series (clause 2), read the status line at the START and again at the END of the series, and report the series as MIXED-INSTRUMENT if they differ.** This is clause 3 meeting a variable none of us controls: the instrument can now change mid-series without announcement, so the only defence is bracketing the series with observations. Clause 1 (freeze the methodology) is unaffected and remains the actionable one.
  - **Do not read shallower lane output as a lane getting worse.** Varying quality under drift is a fleet condition, not a performance problem to correct in a brief or a verdict. Judge the work, not the lane.
  - Harness-produced readings are unaffected — the model authors the code, it does not produce the number.

  3. **Mixed-instrument arms that cannot be re-run are reported as MIXED, never averaged** — averaging across instruments produces a number with nothing wrong in it that describes nothing that happened. This clause outranks convenience: the un-re-runnable mixed series is exactly where every incentive points at averaging and calling it done. Name the model that produced each series in the series record — the PR body or the issue comment carrying the numbers — whichever clauses applied.

## CROSS-PLATFORM AWARENESS (owner standing rule, 2026-09-03)

The owner develops on Omarchy (this machine), Windows and macOS and moves between them. This product ships to all three, so treat it as cross-platform in PROCESS, not only in code. Binding on every review and every spawn brief:

- **Platform note in the PR.** A change touching build config, toolchain versions, native dependencies, filesystem paths, line endings, shell invocation, or platform-gated code must carry an explicit note on what it means for the other two platforms. The RM CHECKS that note as a review item — its absence on such a change is a blocker, not a rider.
- **Pins live in the repo.** Toolchain and runtime versions belong pinned in-tree so a fresh clone builds identically everywhere. Current pins: `engines.node` `^22.19.0 || >=24.0.0` and `packageManager yarn@4.18.0` in the root manifest; CI pins Node `22.23.2` exactly on all five jobs. **Known gap:** `engines` admits any Node ≥24 while CI builds only on 22.23.2, and this machine runs Node 26.8.1 — a lane can produce artifacts and lockfile entries no CI runner or Windows checkout reproduces. Treat a widened `engines` range or a Node-version-sensitive change as a platform note item; consider a narrower pin when the owner next rules on it.
- **Lockfile updates are cross-platform events.** A lock written by a newer toolchain can be unbuildable by an older one (this bit the owner on Windows, 2026-09-03). Any `yarn.lock` change is reviewed as a portability change: say which Node and Yarn wrote it, and whether the entries it moved are platform-conditional (`optionalDependencies`, native builds — koffi, node-pty, electron, sharp).
- **Green CI is not proof of portability.** Say what the gate did and did not cover rather than treating a green rollup as portable. This repo is better placed than most — `check` on Linux, `desktop-windows` and `upstream-command-windows` on Windows, `desktop-macos` unsigned — but macOS runs only the smoke, no signed packaging, and no runner exercises the Node version the lanes develop on.

**LESSON — self-referential faults need an external observer or a deliberate audit (2026-09-03).** On one day, three repos on this machine carried three variants of the same fault, each invisible in a different way: suquo's toolchain pin was **absent**, this fork's was **present and loose** (#87), tsc's was **present and machine-local**. None of our gates could have found any of them, because **every gate runs on the machine whose configuration is the thing in question** — a gate cannot audit the assumption it is itself standing on. All three surfaced only because the owner hit an unrelated symptom on a different operating system and thought to mention it rather than quietly fixing it. That is luck, not process. The standing consequence: for any property that the local environment silently supplies — runtime versions, native toolchains, path semantics, line endings, locale, shell — the RM does not wait for a gate to complain. Either an external observer reports it (the owner's other machines, a CI runner configured differently on purpose) or the RM audits it deliberately, by reading the declared surfaces against each other the way #87 was found. Prefer the audit; it is cheap and it does not depend on someone else's bad afternoon.
